# 识图与自然轮流说话

> 基础识图随既有版本发布；本文自然接话和统一协调器为v2.1.7改进。新安装包正在构建与验收，当前已发布v2.1.6不包含这些改进。发布范围见[文档索引](README.md)与[验证矩阵](validation.md)。

## 实际行为

- 微信图片遵循官方 CDN/AES-128-ECB/PKCS7 处理；QQ 支持图片消息段、CQ 图片、base64 图片和网关 get_image。真实图片通过多模态 `image_url` 输入交给视觉模型。
- 「图片1 → 说明1 → 图片2 → 说明2」保持原顺序和编号；连续几条消息也保持顺序合并，不把全部图片挪到所有文字后面。群聊保留发言者。
- 默认基础静默窗口4秒；短句、未完成句和附件说明6秒。新消息重新计时；最近20个有效发送间隔的中位数×1.5可上调，最多8秒。不会机械地在每句后发送“我在等你”。
- “等我说完”“先别回”“还没发完”等独立表达进入明确等待状态。后续几段文字不会自动解除；用户最后说“说完了”“可以回答了”等时尽快处理。超时从明确等待指令开始计算，默认120秒，不因每条续话无限延长。
- 原10秒仅触发内部评估，不强制发送，也不关闭新输入抢占；50条只是预处理分段，不是发言结束。明确等待默认120秒后重判，不强制发送占位提醒；明确结束约0.3秒接答。用户可在「模型与行为」调整基础窗口、普通最长等待、明确等待超时，窗口0关闭合并。
- QQ 若收到 NapCat 的真实 `input_status` 通知，则把已有待回复批次短暂延后（提示有效期4秒），不生成伪造用户消息、不影响其他人的队列，不将10秒评估当作强制发送边界。
- 接口接收回调不等待 LLM；静默等待不占回复处理槽位。入站与原始批次持久化，停止/重启后续处理。
- 用户在图片下载、解析或模型生成中继续输入，会取消尚未提交的旧请求并重新合并。已提交的消息不撤回；微信已持久化的投递草稿仍按原批次重试，不把新消息混入旧草稿。

## 克制但不冷落

微信和QQ共用「收集→判断→回应/继续等待/仅留上下文→生成→提交」协调器。私聊默认 `reply_mode=natural`，可切为 `always` 每轮必回。QQ群聊仍只在被@时进入回复边界。

明确问题、请求、纠正、直接呼唤、重要分享和明显情绪诉求保障回应；确认、重复和自然收尾可以没有气泡，但保留用户单方上下文。仅对语义模糊的完整表达增加一次现有模型的轻量判定（最多两秒），超时或解析失败不当作拒答。内部 `reply/defer/context_only` 和原因不会作为聊天正文。

普通分享可稍后自然接话：独立默认开启，不依赖随机主动联系；1～3分钟内重判一次，只在有意义时补回，最多一次。10分钟后仅留上下文；明确问题不受此过期规则影响。晚安、不用回、撤销和话题切换取消旧补回。共用免打扰、同人忙碌和持久触达预约；固定原渠道，未知投递不跨端重发，未获回应不继续追发。

生成、识图、搜索与令牌等待期间的新来话使未提交旧稿失效；提交开始后保留原投递凭据。QQ私聊限流12条/分钟、突发2；群聊仍2条/分钟，QQ全局20条/分钟，微信原有限制不变。页面将等待、主动静默、稍后重判与投递结果待确认分开显示。

## 更自然，但不制造额外等待

仅真正决定回复后，超过短暂准备时间才发送平台原生“正在输入”提示；快速回复不闪烁，等待用户说完时不假装机器人正在打字。

微信使用官方 `sendtyping`，结束/取消后尝试关闭；QQ 私聊使用 NapCat 已公开的 `set_input_status(event_type=1)`，结束时停止刷新，消息发送或客户端原生有效期清除。没有使用未核对的停止枚举，也不发送占位气泡。网关不支持时退避重试，不阻碍正文投递。这个辅助状态可单独关闭并热更新。

## 图像清晰度与模型

- 小型 PNG 截图/图表优先保留无损 PNG，透明底合成白色；照片与过大图像使用 JPEG。最长边2048，单图下载上限20MiB、像素上限2000万、归一化上限4MiB、单轮最多6张。
- 「模型与行为 → 图片识别」可填写独立视觉模型/接口/Key；留空使用主模型。DeepSeek 当前官方 `deepseek-flash` 支持标准 Chat Completions 的图像内容块，见[官方视觉文档](https://api-docs.deepseek.com/guides/vision/)。使用其他主模型时应选用支持图片输入的模型。
- 本轮实际图像状态优先于历史读取错误，不用过去的配置提示否定当前识图能力。媒体故障使用自然回复，诊断只留在后台；不把 `[图片]` 占位符当成已经识别，不降级给不支持图片的文本兜底模型。图像字节不写入聊天日志、持久上下文或长期事实记忆；私人待处理收件可保留原始图片引用/入站 inline 数据。
- 对话路径逐图容错、保留原编号：一个图片读取/解析失败不丢弃其余好图，最多读取前6张，其余保留未读标记；并发2、总预算35秒，整轮取消时关闭所有在途任务。严格内部 `load` 入口仍用于要求整批成功的测试/调用。
- HTTP400/413/422拒绝多图请求时，最多逐张读取已提供图像（并发2，总预算25秒），再把实际视觉观察和原始说明合成一条回答；单图仍失败就保留未读状态，不用文本兜底冒充看图。
- 视频独立为附件标记；当前通道未提供视频画面/音轨，不将其送入图片解码、不声称看过视频。继续回答实际收到的图片；需视频分析时自然询问关键截图或片段说明。
- 图片/模型异常对外发送前最多等1.2秒并检查补充输入；即使旧批次达到普通最大等待，新到媒体也会使失败提示失效并重组。正常有效答复同样接受新输入抢占，不因达到10秒评估点而发送旧稿。

## 参考与本项目适配

1. [OpenClaw 按会话缓冲](https://github.com/openclaw/openclaw/blob/main/src/auto-reply/inbound-debounce.ts)：会话键隔离、有序接纳、静默合并和正在处理时的生命周期。这里保持现有 Python/iLink/OneBot 结构，不复制整套框架。
2. [OpenClaw 输入状态](https://docs.openclaw.ai/concepts/typing-indicators)：区分等待、真正开始处理与输入提示刷新周期。
3. [AstrBot 图文合并插件](https://github.com/gongzhudeng/astrbot_plugin_chat_merger)：短句多等、图片与相邻说明有序、平台输入提示。这里没有照搬默认五分钟的图片等待，而采用短图片补充窗口与用户明确控制的等待。
4. [腾讯官方图片实现](https://github.com/Tencent/openclaw-weixin/blob/main/src/media/media-download.ts)：核对图片URL优先级、密钥编码与真实解密。
5. [NapCat 输入状态源码](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/action/extends/SetInputStatus.ts)：私聊 user_id 与 event_type=1；辅助能力不当作正文发送确认。

## 可复用回复约束

```text
把连续输入视为一个尚未完成的发言，按图片、原话与补充说明的顺序理解。
用户明确要求等待时不抢答；结束信号出现后自然接答。
每张图片只陈述实际看见的内容，细节模糊就说清楚，不把猜测作为事实。
图片、视频分别处理；不对聊天用户发送模型配置诊断，不依据视频附件标记编造画面。
不要反复说“收到”“正在处理”“我在等你”，也不把用户的每条短消息分别回复。
普通聊天输出一条自然完整回复，既定人设与跨平台个人记忆保持连续。
```

## 测试边界

测试使用合成图片、加密图片、SDK真实序列化与模拟接口；核对图文顺序、真实像素、回复次数、最新微信 context_token、明确等待/续话/结束/重启、原生输入通知和取消清理。并未以此宣称真实客户端已经显示消息，或替代所配置视觉模型的识别质量评测。

开发新增合成回归覆盖微信/QQ真实SDK序列化、多图400兼容重试、部分坏图、视频分离、微信强制批次的异常提示抑制与晚到媒体合并；没有调用真实付费模型或用户视频。
