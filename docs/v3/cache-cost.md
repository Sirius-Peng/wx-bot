# 请求、缓存与费用：v2.1.7核查及v3调整

更新：2026-10-25；费用代码核查初次记录：2026-10-23。本文区分历史v2.1.7与当前发布v3.0.0；本次安装包和未执行项目见[本次发布清单](../release-v3.0.0.json)。修改源码不会改变旧安装包；下文固定源码核查与离线桩测试是原日期记录，不是用户账单归因、实际省费比例或真实API总体时延验收。

## 17M token、约30元能说明什么

用户反馈的是混合token总量及总金额。即使相除，也只能得到该段用量的混合单价，不能反推缓存命中率，或确定主回复、思考、搜索、判定和后台整理各占多少。不同输入、缓存输入、输出及服务功能的计价可能不同；具体结算以对应时段的[DeepSeek官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)及供应商账单为准。

要判断成本来源，需要同一时段的请求数、任务类别、输入/输出token、真实缓存hit/miss，以及缺失用量的请求情况。仅凭“模型相同”“一直开着会话”或“token很多”，都不是命中或未命中的证据。

旧版一次搜索的常见路径是：主模型决定调用工具 → 辅助搜索模型读取并总结 → 主模型整合 → 主模型固定复核，即三次主模型请求加一次辅助搜索。两次辅助搜索可能是四次主模型请求加两次辅助搜索；这些计数不包括接话判定、记忆、压缩及网络重试。**开启搜索不等于每条消息都会搜索**：未触发工具的普通聊天仍可只有一次主回复。

旧版也不是每个入站文字碎片都调用判定模型：收集完整发言后，明确诉求、确认与收尾等先走规则，只有模糊私聊再判断。记忆整理原本就有至少三轮、空闲两分钟及同人五分钟间隔；不能把它描述成逐句抽取。当前v3曾出现的逐快照投机调用问题不属于用户安装的v2.1.7。

## 当前v3减少哪些无效工作

### 1. 保留用户选择，内部任务短而非思考

日常主回复默认`fast`；用户仍可选择`deep`，主模型、独立判定/视觉配置和Key均保持可配置，不为节省而强行替换。对已识别支持的官方DeepSeek接口，fast主回复及内部判定、记忆、压缩和辅助搜索明确使用非思考选项；不向未知兼容服务硬塞专用参数。

思考模式配合工具时保留服务要求的`reasoning_content`、工具调用和`tool_call_id`等协议字段，不把它们显示为聊天正文。缺失协议状态可能引发400错误或重复尝试，不能靠丢弃这些字段“省token”。会话中保留模型原输出时，必须与实际发送正文在规范化后等价；有实质改写就不能把另一份原稿冒充已发送回答。这样尽量维持后续前缀一致，但不承诺服务缓存一定包含或命中此前输出。

### 2. 同一连续输入批次只有一次云判定额度

明确问题、请求、更正、呼唤和情绪诉求先由规则保障回应。模糊私聊默认使用`deepseek-flash`的短`R/D/C`协议，整个判定阶段最多3秒；等待窗口约0.8秒防抖后可与图片预取和本地检索并行。

同一待回复连续输入批次按会话和第一条原始消息识别，只开放**一次云判定额度**，仅在真正发起底层调用前扣除；防抖中取消不消耗额度。新片段使旧版本失效，但不重新开放该批次额度，也不复用旧片段的静默结论。最新完整内容仍检查保护、确认和未完句等规则；额度已用且语义模糊时保守回应，诊断标为`conservative / burst_budget_exhausted`，不是云命中或缓存命中。超时、异常或无关记忆文件变化不为同批次再付一次判定调用。

完全相同且仍有效的成功预判只交接使用一次。新批次、独立的稍后重判另行判断；预算有有界保留期和容量，不是永久禁止后续接话。取消客户端工作也不表示供应商一定未收到或不会计费，仍需结合真实usage核对。详见[接话策略](local-decision.md)。

### 3. 稳定前缀，不为缓存制造冗余内容

完整人格与已发送会话保持稳定，新时间、召回和本轮媒体资料只追加在尾部。默认达到配置窗口的40%再压缩；官方已识别的`deepseek-flash`/`deepseek-v4-pro`自动使用1M，未知模型保守32K，可手填窗口及压缩比例。请求体、图片数或真实模型限制仍优先，不能为保留缓存而发送超限内容。

不为了命中填充无意义pad，也不为了显示低token而提前反复滑动/改写历史。压缩用于控制有效上下文与质量，不是无限堆积所有旧资料。明确遗忘、人格或供应商/模型变更必须使旧会话失效；不得为了缓存继续发送不应使用的信息，不跨用户复用私聊会话。完整语义和媒体边界见[稳定会话与KV缓存](context-session.md)。

### 4. 搜索有依据地总结，合格答案不固定再改一遍

**2026-10-25补充：** 默认已升级为直接Search / Fetch（`search_backend=tools`），不额外调用native辅助模型；原辅助模型仍可手动选择。直接工具按请求次数单独计费，主模型整合仍有token成本，失败不自动切另一个后端。Search与Fetch整轮合计最多两次工具操作；明确408/429/5xx每次操作可有一次有界重试并逐次记录，无响应网络错误或超时不重试，重试不承诺免费，见[1017工具升级](search-1017.md)。下述10月23日缓存/按需复核仍描述兼容native路径，不能把其1024输出上限或模型usage套用到直接工具。

继续按需联网并读取正文摘要与证据，正常完成一次整合；证据不足才补搜，成稿不合格才进行一次有界修订，不退回标题/链接清单。后台记忆、压缩及判定不因主聊天开启搜索而递归搜索。

成功的公开query结果可在本进程短缓存60秒，相同在途请求采用single-flight合并；不跨搜索Key或模型复用，不把失败当成功缓存。仅提交必要公开关键词，不缓存整段私聊、人格、记忆或图片。公开query筛查是附加保护，不代表客户端能完美判断所有自然语言的隐私含义。搜索连接复用减少重复握手；新输入仍能取消旧工作。

这里的**本地搜索结果缓存不是供应商KV缓存**。命中搜索结果可以避免重复辅助检索，但主模型整合回答仍可能有调用和输入成本；60秒也不是承诺结果永久新鲜。不会将这类复用计成`prompt_cache_hit_tokens`。搜索协议和历史版本区别见[搜索与时间](../web-search-time.md)。

## 如何查看当前运行的真实用量

在v3「设置 → 主模型 → 用量与缓存诊断」展开后点击**手动刷新诊断**；不自动轮询、不为刷新调用模型。按任务区分聊天、接话判定、记忆、搜索规划/读取/整合/复核、压缩与主动联系等已观察请求。

- 只计接口实际返回的usage。输入、输出、缓存hit/miss、思考等缺失字段显示**未知**，不补成0，不按模型名推算价格。
- 缓存比例按已知输入token加权：同一覆盖范围内的命中token总数除以输入token总数，而不是每次命中率的算术平均。分母只用明确输入总量或明确hit+miss；矛盾数据不当作有效分母。
- 明确区分“已知样本命中率”和“总体命中率”；覆盖不完整时，总体仍为未知。必须同时看已知/未知请求数量，不能将少量完整样本冒充全部调用。
- 思考token是输出token的**子集**，不要再加到输出上重复计算。缓存命中输入也已经属于输入，不再额外加一次。原生搜索不同协议的缓存创建/读取字段分开保留，缺失不填零。
- 当前运行只保留近期最多**500条事件**，不是账户历史账单或永久费用账本；重启、窗口外事件、超时/取消后未返回的usage和其他客户端的请求，都可能不在统计范围。未知不代表免费。

HTTP连接、客户端会话ID、本地搜索缓存及模型名称都不是KV命中的证据。服务端缓存尽力而为，只有服务真实返回的缓存用量才纳入统计。[DeepSeek缓存说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

## 验证与发布边界

历史tag桩测试能证明旧请求装配、固定复核和未显式禁思考；连续输入桩测试能证明当前批次额度与取消机制。它们不调用付费API，不能证明真实缓存率、账单节省、首token或完整回复速度。正式比较须在相同公开输入、模型/模式及冷暖条件下记录请求数、任务类别、真实usage和端到端耗时，并与供应商控制台同一时段对账。

当前没有公布这些改动的实测省费百分比，也没有将v3行为追溯套用到v2.1.7安装包。后续数据与原生/安装包结果按[验收记录](validation.md)补充；原有主模型、Key、人格、应用ID及用户数据路径保持不变。
